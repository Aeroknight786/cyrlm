# Research behind the triaLM refactor plan (2026-11-06)

Condensed results of nine research tracks run for docs/PLAN.md. Numbers marked as claims are self-reported by their authors; see each section's sources.



## research:engines-avalon-strata

I read both engines' own docs, the model's config, and the published numbers. Avalon and Strata both run one model, Qwen3.8-Flash-Next, on a single consumer GPU. The model is 125B parameters with 6B active per token, plus a 51B n-gram table and a 4B MTP layer. It has 48 layers (36 Gated DeltaNet and 12 sparse-attention layers), 512 experts per layer with 10 active plus 1 shared, and hidden size 2560. Both engines use the same method: about 3.5 to 4.8 GB of always-read weights and the KV cache stay on the GPU, all 24,576 experts sit in system RAM, the leftover VRAM holds a cache of the most-used experts, and the CPU computes the cache misses while the GPU computes the hits. The model's own MTP layer drafts tokens for speculative decoding. Avalon is a llama.cpp fork (MIT), built from buun-llama-cpp and tuned for RDNA3/ROCm. It runs one ~89 GiB IQ3_KS hybrid GGUF plus a 1.48 GB MTP file, launched as `llama-server` on 127.0.0.1:8080. On an RX 7900 XT with PCIe 3.0 and 64 GB DDR4 its author reports 66.1 tok/s without MTP and 98.4 with it, and about 1,850 tok/s prefill. On a rented RTX 4090 it reports 141.9 tok/s. Strata is a different kind of project: a full product with a desktop app, a `strata` terminal CLI and an engine, covering NVIDIA RTX 20-50, AMD RDNA2-4, Intel Arc, Apple Silicon, Strix Halo and DGX Spark. It serves `/v1/chat/completions`, `/v1/messages` and `/v1/responses` on 127.0.0.1:8080, offers ISTA-DASLab Q2_0, IQ2_XS, IQ3_XXS and IQ3_S plus Unsloth, Gyro, Swift and NVFP4 packs, and has a calibrate/tune step and BENCH scripts. Its paper reports 94.6 tok/s on a 12 GB RTX 5070 at 4K context with Q2_0. Strata's paper and QUANTS.md publish a per-token byte breakdown, the measured hit rate (the share of experts served from VRAM: 0.72 adaptive on a 12 GB card), CPU expert throughput (about 42 GB/s for Q2_0 with AVX-512, about 5 GB/s per core for i-quants), the PCIe share formula, and an overall efficiency of 35-40% of the bandwidth bound. That is enough for cyrlm to simulate these engines from first principles instead of calling CPU offload unpredictable. MTP is not required but adds 1.4-1.8x on these offload engines; acceptance is 0.55-0.65 on prose and up to 0.95 on code, and it costs about 0.7-1.5 GB of VRAM. YaRN is documented by Qwen (factor 4 for 1M context) and as an experimental option in Strata; stock llama.cpp flags for it exist in Avalon's llama-server. All speed numbers come from the authors or users. They are dated and change quickly: Avalon revised its own 16/32 GB RAM claims within weeks. cyrlm should store each one as a versioned, sourced claim. Of the similar engines, I could not find sqwen-moe-3090 or WinMoE. I found Lamina, NInfer, Merlin, MoE4All, Splash, buun-llama-cpp, ik_llama.cpp and KTransformers.

### Implications
- Replace the current 'offload = no-claim, 1/(1+6·frac)' branch in internal/predict/predict.go with a real MoE hybrid model. Inputs: dense bytes per window, expert bytes per token, total experts, cache slots from free VRAM, a hit-rate curve h(slots) plus an adaptive bonus, CPU expert rate R (quant- and ISA-dependent), PCIe L with Strata's p = L/(L + kR), MTP τ from (k, α), and fixed per-window overhead. tok/s = τ / [D/(BWv·η) + max(cached, cpu, pcie) + t_fixed]. Calibrate one efficiency set per engine, because stock llama.cpp `--n-cpu-moe` is 3-4x slower than Strata on the same R9700.
- Add golden calibration fixtures as unit tests that must reproduce within ±15%: Strata RTX 5070 Q2_0/IQ2_XS/IQ3_XXS at 1K-262K, including Table 5's ms breakdown and hit rates; Avalon 7900 XT 66.1/98.4 and its 250k numbers; Avalon and Strata on the 4090 (~98 no-MTP, ~142 MTP); R9700 IQ3_S 94.6 at 8K; the 16/32/64 GB RAM cases (49/88/99 tok/s). This is how cyrlm 'simulates the Reddit fast-config claims' credibly.
- Model the context cost: KV bytes per token (~13 KB at 8-bit, QSA layers only) take VRAM from the expert cache, so h drops and decode falls (Strata 12 GB: 94.6 -> 56.3 at 262K). Long context and YaRN (>262K) should visibly cost speed in the requirement picker. Stock llama.cpp flags (`--rope-scaling yarn --rope-scale 4 --yarn-orig-ctx 262144`) exist in Avalon's llama-server; Strata documents YaRN as experimental.
- Ship 'engine recipes' as data, not code, one per engine. Fields: OS/arch matrix (Avalon: Linux + ROCm 7.x + gfx1100-1102/1200/1201 + AVX2, CUDA build by hand; Strata: NVIDIA RTX20-50, AMD RDNA3/4, Intel Arc, Mac, Strix Halo, Spark); RAM/VRAM/disk gates (Avalon >= 14 GiB RAM, ~98 GiB disk, >= 19 GB VRAM for 256K+MTP; Strata experts + 10 GB); exact install, plan, run and stop commands; port 8080 and endpoints; tunable knobs (MTP on/off, -c, -ub, KV type, pcie-frac); and claims with {source URL, date, engine version, hardware, measured | user-reported | estimate}.
- Make the low-friction CLI drive each engine's own non-interactive path instead of an agent. Strata: `sh install.sh` -> `strata launch --plan --family qwen --model <q> --output json` (show the plan) -> `strata launch ... --yes --no-tui --port 8080` -> `strata connect <harness> --check --output json` -> `strata launch --status|--stop`. Avalon: `AMDGPU_TARGETS=... MODEL_DIR=... bash install.sh` (no prompts) -> `avalon-server`. Ask for one confirmation for the big download (66-97 GB) and nothing else.
- Requirement-first picker: the user picks needs (coding agent vs chat, context 32K/128K/256K/1M, quality floor, speed floor, GPU vendor, RAM/disk budget). cyrlm then ranks configurations (engine × quant × MTP × context × KV type) by simulated tok/s, TTFT and fit, and shows the claim it reproduces. For example: '7900 XT + 64 GB -> Avalon IQ3_KS + MTP, 256K: ~98 tok/s short, ~81 at 250k'; '12 GB NVIDIA + 64 GB -> Strata Q2_0 + MTP: ~93 tok/s at 4K'; '32 GB RAM -> Strata Coder IQ1_M, or Avalon with the arena (88 short, 40-50 after a long prompt)'.
- Default MTP on for these offload engines (+40-80%), and model it as a workload-dependent multiplier: prose α ≈ 0.6, code α ≈ 0.8-0.95. Charge its VRAM (0.8-1.5 GB) against the expert cache, so the simulator can answer 'is MTP necessary?' per machine and workload.
- Close the loop in cyrlm verify. Read Strata GET /metrics (hit_rate, pcie_share, drafts_offered/accepted, ram_blobs/file_blobs) and the response `timings`, or llama-server /metrics, /slots and timings for Avalon. Fit the user's real h, α and efficiency, then re-predict other configurations on that machine.
- Trial pacing: OpenRouter likely has `qwen/qwen3.8-flash` (unverified id; the hosted sibling has 1M context), not the exact Flash-Next open weights or quant. Label the trial as same family, hosted precision, and show the quant's perplexity delta (IQ3_KS 1.443 vs Q4_K_XL 1.316 English) next to the paced speed.
- Harness wiring, from Strata's tested configs: Claude Code needs CLAUDE_CODE_MAX_CONTEXT_TOKENS; Codex needs wire_api=responses, model_context_window and stream_idle_timeout_ms=600000 (long first prefill); OpenCode needs limit.input. Avalon's llama-server documents /v1/messages and /v1/responses, so the same harness configs should work; check each with a cyrlm 'one prompt + one tool call' probe, like `strata connect --check`.
- Treat engine numbers as fast-moving. Pin each claim to an engine version and date, and re-fetch the READMEs with raw.githubusercontent.com when cyrlm updates its catalog (Avalon's headline went 91 -> 98 and its RAM claims were corrected within about two weeks).

## research:fast-config-techniques

Catalogue of the 2025-2026 "fast local LLM config" techniques for coding-agent use (10-60k-token prompts, many turns, tool calls), checked against llama.cpp master docs and source (fetched 2026-11-06), ik_llama.cpp, KTransformers, TabbyAPI/ExLlamaV3, mlx-lm, vLLM and Ollama sources, Hugging Face model cards and discussions, and r/LocalLLaMA claims. Reddit, unsloth.ai, github.com HTML and most blogs are blocked from the sandbox (reddit.sentinel-team.org, unsloth.ai, aiweekly.co, cloudmagazin.com, *.hf.space and github.com discussions all failed), so community numbers come from WebSearch snippets and are marked claim-only. Seven findings matter most for cyrlm. (1) MoE expert offload (--n-cpu-moe / -ot exps=CPU) can be predicted, so cyrlm should stop labelling it "unpredictable". Decode is a sum of GPU bytes over GPU bandwidth plus CPU bytes over RAM bandwidth. Prefill is bounded by PCIe: llama.cpp copies CPU-resident weights to the GPU for every micro-batch of 32 tokens or more (GGML_OP_OFFLOAD_MIN_BATCH, checked in ggml-cuda.cu). My formula reproduces a community gpt-oss-120b/RTX 3090 -ub sweep within -16%..+2% and decode within about 15%. (2) The -ub/-b size is the biggest prefill lever in hybrid setups: 380 to 2091 tok/s from ub 512 to 8192, for a small decode cost. It also sets a per-turn latency floor of W_cpu/B_pcie, which hurts agent loops built from many small tool results. (3) Speculative decoding depends on the case. MTP (llama.cpp --spec-type draft-mtp, merged May 2026) gives 1.6-1.9x decode on dense Qwen3.6-27B on a GPU, but only about +27% on the 35B-A3B MoE. It costs about 22-25% of prefill speed and context/VRAM, and needs -np 1. The verify step on an MoE touches about (k+1)x as many experts, which explains the gap. N-gram drafting gives 0-50% depending on how repetitive the text is, and cyrlm can measure that exactly from the user's own trial transcript. (4) Engine choice: llama.cpp/llama-server is the only runtime exposing all the hybrid knobs; Ollama has no expert-placement, ubatch or spec knobs, and one test measured 9.8 vs 22 tok/s. vLLM/SGLang/ExLlamaV3 help when the model fits entirely in VRAM, with ExLlamaV3 strongest on prefill. KTransformers and ik_llama.cpp are for very large MoE models on big-RAM CPUs. MLX decodes about 8-15% faster on Macs. (5) Prompt-cache correctness dominates agent speed. Claude Code's attribution header breaks llama.cpp prefix reuse unless CLAUDE_CODE_ATTRIBUTION_HEADER=0 is set. Hybrid and sliding-window models only roll back to saved checkpoints. (6) Flags change between llama.cpp versions: --draft-max is removed in favour of --spec-draft-n-max, --no-mmap/--mlock are now -lm/--load-mode, and --fit is on by default. Recipes therefore need a version range and a flag-translation layer. (7) YaRN is a context-capacity tool, not a speed tool, and static YaRN may cost short-context quality. There are 18 shippable recipes below, each with hardware, model, engine, flags, claimed prefill and decode, source and confidence.

### Implications
- Replace the 'offload = no claim (2-7x errors)' rule in internal/predict (AccuracyFor's offload branch) with a placement-aware hybrid model. Decode: t = (B_gpu + KV(d))/(eta_g*BW_g) + B_cpu/BW_cpu_eff + t0. Hybrid prefill per ubatch: W_cpu/B_pcie + ub*t_gpu_tok when ub >= GGML_OP_OFFLOAD_MIN_BATCH (32), otherwise CPU compute. It reproduces the gpt-oss-120b/3090 -ub sweep within -16..+2% and decode within about 15%. Label it 'predicted, calibrate' (about 25%) instead of no claim.
- Add hardware facts the new model needs to internal/hw. Per-GPU PCIe gen and width (nvidia-smi --query-gpu=pcie.link.gen.current,pcie.link.width.current; lspci -vv; rocm-smi), and P2P/NVLink topology (nvidia-smi topo -m). Populated memory channels and speed (dmidecode -t memory or the WMI equivalent), physical vs logical cores, NUMA nodes (lscpu), ISA flags (avx512f, amx_tile from /proc/cpuinfo), free RAM, and OS. Flag Windows+NVIDIA for the sysmem-fallback risk. Keep the existing bandwidth probe as the CPU-bandwidth calibration.
- Build the model-architecture database from OpenRouter plus Hugging Face, since OpenRouter metadata lacks what the roofline needs. Use OpenRouter's hugging_face_id to fetch config.json from huggingface.co (reachable): num_hidden_layers, num_experts / num_experts_per_tok / shared experts / moe_intermediate_size / first_k_dense_replace, attention heads and KV heads / head_dim, sliding_window and layer_types (linear attention), num_nextn_predict_layers (MTP present?), rope_scaling and max_position_embeddings. Read GGUF tensor sizes through HTTP range requests (internal/gguf) to get exact per-layer expert bytes for each quant.
- Ship a llama.cpp hybrid optimiser: given VRAM, RAM, PCIe, the model and the harness scenario, search n_cpu_moe in [0, L], ub in {512, 1024, 2048, 4096, 8192}, KV type, context and spec type. Minimise simulated session time (the existing RunScenario) subject to VRAM >= nonexpert + KV(ctx) + (L-N)*expert_layer + compute_buf(ub) + margin, and output exact flags: '-ngl 999 --n-cpu-moe N -b U -ub U -fa on -ctk .. -c ..', with -fit off or a -fitt margin. Show per flag what it buys, e.g. 'ub 4096: prefill 380 to 1680 tok/s, decode -3%'.
- Add a recipe/preset data file (like internal/runtime/profiles.json). Fields: id, title; hardware predicates (GPU VRAM range, unified memory, RAM minimum, PCIe minimum, OS); model (OpenRouter id + GGUF/MLX/AWQ repo:quant); engine + version range; args[] + env{}; claimed {prefill@depth, decode@depth}; source URL + date + confidence (verified/likely/claim-only); quality notes; 'bottleneck moved' text. Seed it with the 18 recipes here. cyrlm ranks recipes against the user's detected hardware and its own prediction, and prints 'claim vs our simulation' with a warning when they differ by more than 30%. That is the 'simulate and understand the Reddit claims' feature.
- Requirement-first flow: the user picks a harness (sets base prompt and min context), a speed target (e.g. decode >= 30 tok/s, follow-up TTFT <= 10 s), a quality tier, a context need and offline/privacy. cyrlm enumerates engine x quant x placement x spec x KV combinations, shows a Pareto front (session time vs quality vs context), and launches the trial for the chosen point directly.
- Model speculative decoding inside the trial pacer instead of as a static multiplier. Speedup = E(alpha,k)*t_tok/(t_verify(k+1) + k*t_draft + t_ovh), with an MoE verify term U(k+1)/a with U(n) = E(1-(1-a/E)^n). Add an MTP prefill penalty of about 0.78x, version-gated, and an np=1 constraint. For n-gram methods, compute acceptance exactly from the real OpenRouter outputs and the context of the user's trial: replay ngram-simple/ngram-mod with the internal/tok tokenizer, then answer 'MTP / n-gram: worth it for YOU?' with a per-session net delta.
- Model the per-turn PCIe floor for hybrid MoE in the pacer. Every follow-up prompt of 32 tokens or more pays at least W_cpu/B_pcie (for example about 1.5 s for 44 GB at 30 GB/s), which dominates agent loops with small tool results. Offer the GGML_OP_OFFLOAD_MIN_BATCH env tweak, which lets small deltas run on the CPU, and simulate its trade-off.
- Add a 'cyrlm tune' CLI step with no agent and no extra approvals. Run llama-bench (-o jsonl) sweeps over -ub, --n-cpu-moe, -fa, -ctk and -t (ik_llama: llama-sweep-bench), fit B_pcie, BW_cpu_eff, eta_g and the MoE ub-efficiency r0, save the winning config, and re-predict. When pointing Claude Code at a local runtime, write CLAUDE_CODE_ATTRIBUTION_HEADER=0 into the env block of ~/.claude/settings.json (or pass --settings); otherwise simulate a full re-prefill every turn. Use vLLM or SGLang only with NVIDIA/ROCm, full VRAM fit and a need for concurrency or a trained drafter (AWQ/GPTQ-Marlin on Ampere, FP8 on Ada+, NVFP4 on Blackwell). ### Open questions
- Effective PCIe host-to-device bandwidth on real consumer boards (pinned vs pageable, chipset-attached x4 slots, x8/x8 bifurcation). The formula fits the 3090 sweep at about 30 GB/s, but cyrlm cannot measure it from stdlib Go without a GPU probe. Could it be derived from a 2-point llama-bench -ub sweep?
- Does llama.cpp overlap the expert weight copy with compute during op offload? The data fits a sum better than a max, but the GLM-4.6 4-GPU run (333 tok/s at ub 4096) is slower than a pure-copy estimate, which suggests a slower primary-GPU link or CPU-side work.

- ik_llama.cpp vs mainline hybrid prefill is contradictory (166 vs 572 tok/s and the reverse). It needs a controlled sweep before cyrlm recommends ik for anything but very large MoE models.

- Strix Halo prefill: which build/env combination (rocWMMA FA, hipBLASLt, RADV vs AMDVLK, ROCm version) is best per model is still disputed. This needs a matrix in the calibration probe.

## research:mtp-spec-yarn

Spec decoding is not necessary for cyrlm. It is worth offering as a clearly labeled optional speed-up, and only some setups gain much from it. In cyrlm's own predictor, decode is 55-84% of each Claude Code turn on discrete NVIDIA GPUs once the prompt cache works, but only 20-43% on Apple Silicon, where prompt processing dominates. So end-to-end savings follow saved = f_decode*(1-1/S) - p*f_prefill, not the decode speedup headline. Speedup model: S = tau(alpha,k)/(1+k*o), with tau=(1-alpha^(k+1))/(1-alpha) and o = draft plus extra verification cost per drafted token, relative to one target token. Fitted to public measurements: o is about 0.3 for a dense hybrid 27B on an RTX 3090 (1.67x at k=2) and about 0.55 for a 3B-active MoE (1.17x on an RTX PRO 6000, about 1.1-1.35x elsewhere), because each extra verified token pulls in different experts. On Apple Metal with llama.cpp, o is about 0.8, so MTP was slightly slower (0.93x). That gives about 20-35% wall-time saved for dense models on NVIDIA (more with thinking output), about 4-11% for A3B MoEs, and about 0% (or a loss) on Mac llama.cpp. MTP is now real and mainstream. llama.cpp merged MTP (PR #22673, May 2026) as --spec-type draft-mtp. Current master has MTP graphs for GLM-4.x MoE, DeepSeek V3-family, Qwen3-Next, Qwen3.5/3.6, MiMo-V2, Step-3.5, Nemotron-H MoE and Gemma 4. vLLM ("method":"mtp") and SGLang (NEXTN/EAGLE) have it, and Ollama has draft_num_predict. mlx-lm does not: it strips the mtp.* weights. Not every config that mentions MTP ships the weights: MiniMax-M2 and Qwen3-Coder-Next have none, and Kimi K2 has 0 MTP layers. Model-free n-gram speculation (llama.cpp ngram-mod, vLLM ngram/suffix) costs no memory and fits agents, whose Edit/Write calls copy text already in context. cyrlm can simulate it exactly, because it sees the real tokens. YaRN matters mainly for the 32K-native coders (Qwen2.5-Coder, original Qwen3 dense and 30B-A3B, MiMo-7B, Ling-flash-2.0), which cannot even hold Claude Code's ~33k prompt plus a session. Models that ship with YaRN (gpt-oss, DeepSeek, Kimi, Devstral 2 / Small 2) and models with 256K native context need nothing. The YaRN flag itself costs no speed. What costs is the extra context: KV memory, decode slowdown at depth, and attention growing with depth during prompt processing. Static YaRN also carries an unquantified short-context quality risk, so cyrlm should offer it only when the harness needs more than the native length, with factor ≈ needed/original.

### Implications
- Add a 'Speed boost' requirement with three choices: off, safe (default), max. Never present it as necessary. Show what each choice does to this task's wall time, not a raw tok/s headline. Example: 'MTP: writes 1.67x faster -> this 40-call Claude Code task about 21% faster (5 s tool time per turn)'. Alongside it, show a per-turn breakdown bar (prompt processing | writing | tools) so users see why a Mac gains little.
- Catalog: per model, add `Spec{MTPLayers int; MTPWeightsShipped bool; MTPGGUFRepo string; EAGLE3Drafts []string; DraftCandidates []string}`. Fill it from HF config keys (num_nextn_predict_layers, text_config.mtp_num_hidden_layers, num_mtp_modules/use_mtp). Confirm weights against model.safetensors.index.json (mtp.* / layers.N.eh_proj), because MiniMax-M2 and Qwen3-Coder-Next have none. For GGUFs, use the existing NextNPredictLayers + trailing-block bytes.

## research:openrouter-catalog

OpenRouter can serve as cyrlm's model database. I found a current raw copy of its live catalog: the hourly poller github.com/dthinkr/openrouter-uptime commits the full /api/v1/models response plus every model's /endpoints response, and I used the poll from 2026-11-06 20:46 UTC. That catalog has 458 entries. Dropping the :batch and :free variants leaves 377 unique models, and 155 of those (41%) name a Hugging Face repo in `hugging_face_id`. models.dev marks 9 more as open-weight even though they lack an HF id. I checked all 155 HF ids, not just a sample of 25. 94% have at least one GGUF repo tagged as a quantization of them. 89% pass a strict automatic match: an allowlisted quantizer (official org, unsloth, bartowski, ggml-org, lmstudio-community, mradermacher), a normalized name match, and no finetune markers. 87% have an MLX repo (71% from mlx-community or lmstudio-community). In a 25-repo deep sample, every weight file's quant tag came out of cyrlm's existing regex once the split suffix and folder are stripped. Without that stripping, cyrlm's FileTag returns "" for every split file (13 of 25 repos have splits). Repos also ship extra GGUF files that a matcher must not treat as weights: mmproj (9/25), imatrix (10/25), and speculative-decoding drafts (mtp- 2/25, dflash- 1/25, eagle 1/25). OpenRouter is a weak guide to what people run locally: only 29 of the 83 most-downloaded text/VLM GGUF base models are hosted there, and 8 of cyrlm's 24 current OpenRouter ids no longer exist. Per-model endpoints declare a precision (fp8 336, unknown 249, fp4 146, bf16 76 of 852 open-weight endpoints). Only 34% of open-weight models have a bf16/fp16 endpoint, 48% top out at fp8, and 13% declare nothing. Completion prices for the same model differ by 1.88x (median) to 8.19x (p90) across providers, so pinning a provider and costing the trial must both happen per endpoint. GGUF header reads over HTTP ranges cost 4–7 requests and about 5–20 MB per file. Dense models can reuse one header across quants (within 1.3%), but MoE quants need their own read (errors of -22% to +37% otherwise). The design I recommend: a CI-generated embedded index keyed by HF id. On the user's machine it is refreshed from OpenRouter (about 80 KB gzipped, cached 24h) and filled in on demand for new models. At trial time cyrlm fetches that model's /endpoints (about 4 KB) to pick the provider.

### Implications
- Key the catalog by the lowercase HF base repo id. Each entry holds: OpenRouterIDs []string and CanonicalSlug (from hugging_face_id, the models.dev [[weights]] URL, or a curated overrides.json); GGUFRepos []{Repo, Role official|unsloth|bartowski|ggml-org|lmstudio-community|mradermacher}; Quants []{Tag, Files []{Path, Bytes, SHA256}, Bytes, ReadBytesPerToken, Measured}; Aux {MMProj, Draft []{Kind mtp|dflash|eagle, Path, Bytes, Arch, NextN}, Imatrix}; MLX []{Repo, Bits, Mode, Bytes}; NativeCtx, RopeScaling, HostedCtx []int; a provenance tag per field (gguf-header|hf-tree|hf-config|openrouter|models.dev|curated); HFSha; IndexedAt.
- Rewrite tools/catalog-gen to discover models instead of reading the hand list in `sources`. Steps: (1) GET openrouter.ai/api/v1/models?output_modalities=text, no key needed; drop :free/:batch/:thinking; keep entries with hugging_face_id, plus models.dev open_weights to fill 9 missing ids. (2) Discover GGUF via HF base_model:quantized:<id>&filter=gguf with an author allowlist, a normalized name match and finetune-marker rejection (measured 89% acceptance). (3) Read the tree for sizes and sha256. (4) Read the header for the default quant, opening every shard and merging with MergeSplits. For MoE, also read each offered quant (cap about 6); for dense, scale by ratio. (5) Emit an embedded index of about 150 entries (est. 0.4–0.6 MB raw; embed gzipped). Budget: about 150 geometry reads plus about 400 MoE quant reads at roughly 12 MB and 1–2 s each, about 6–8 GB and 15–25 min on 8 parallel workers. Run it as a weekly CI job that opens a PR with the diff.
- Fix FileTag before scaling up. Strip a trailing -\d{5}-of-\d{5} and the parent folder before applying the regex; upper-case the result ('bf16', 'f16'); add TQ\d_\d. Classify by basename prefix before tagging (mmproj-, mtp-, dflash-, eagle, imatrix), so draft and projector files never count as quants. Treat unsloth's first shard as metadata-only (0 tensors).
- At runtime on the user's machine: ship the embedded index so the CLI works offline. When the cache is older than 24h, refresh ~/.cache/cyrlm/openrouter/models.json (80 KB gzipped) for prices, new models and availability. A new model with no geometry gets enriched when the user picks or inspects it: HF discovery plus 1–2 header reads (about 10–40 MB, 1–5 s), cached under ~/.cache/cyrlm/hf/<repo>@<sha>.json, so a cache entry only goes stale when the repo's sha changes. At trial start, fetch /endpoints for the chosen model (4 KB, 1h TTL).
- Provider pinning at trial start: pick endpoints from /endpoints that (a) have tools in supported_parameters and supports_tool_choice.auto when the harness sends tools; (b) have context_length ≥ the planned local context but are not YaRN-extended when the local setup is native (Qwen3-32B: choose a 40960 endpoint, not 131072); (c) match the local quant's precision tier: BF16/Q8_0 locally → bf16/fp16, then fp8; Q4–Q6 → fp8, then bf16; avoid fp4/int4/unknown unless they are the only choice. Then sort by uptime_last_30m and price. Send provider{only:[tags], allow_fallbacks:false, require_parameters:true}. Show a fidelity line such as 'cloud: fp8 (declared) vs your UD-Q4_K_XL', or 'precision undisclosed' for the 13% of models that declare nothing.
- Estimate trial cost from the pinned endpoint's prices, not the model-level price; spreads are 1.88x median and 8.19x p90. Cost = uncached_prompt×prompt + cached×input_cache_read + completion×completion (+ internal_reasoning where priced). Example: a coding session with 2M prompt tokens (mostly cached) and 60K output on qwen3.6-35b-a3b deepinfra/fp8 ($0.10/$0.95 per M) costs about $0.26. Show a live running total from each response's usage, and a pre-trial estimate.
- Requirement filters for 'pick what you need', all computable from the index: fits my machine (size and KV from geometry), tool calling (endpoint supported_parameters plus template), reasoning, context ≥ N (native vs YaRN), vision (needs an mmproj file), speculative decoding available (MTP/dflash/eagle drafts or nextn_predict_layers>0), license/open_weights, and coding rank (OpenRouter sort=coding-high-to-low / benchmarks field, Artificial Analysis indices).
- For speculative-decoding (MTP) recipes, index draft files with their bytes and architecture (e.g. gemma4-assistant with nextn=4, 0.25–0.86 GB; Qwen3.8 MTP 1.37 GB) and the main GGUF's nextn_predict_layers. The predictor can then add draft memory and an acceptance-rate speedup as a toggle in each recipe, which answers the 'is MTP necessary?' question with numbers.
- Ollama alignment: always pull via hf.co/<repo>:<tag>, which needs no mapping. Recognize already-installed models by matching blob sha256 against HF lfs.oid; keep Ollama library tags only in curated overrides. Do not use GGUF general.base_model.* for mapping.
- Unhosted models (later phase): 65% of popular local text/VLM GGUF bases are not hosted. Mark them trial=stand-in, use the nearest hosted model in the same family with a clear label, and repair the 8 broken OpenRouter ids in the current catalog (only nemotron is fixable by reverse HF-id lookup; the other 7 need stand-ins).

## research:cli-ux

Today cyrlm has 19 commands, 'cyrlm' with no arguments just prints usage and exits 2, and the main path is an agent prompt (cmd/cyrlm/agent_prompt.md) that tells the agent to ask before every step. I traced one real flow (Codex on a Mac, llama.cpp not installed) through `cyrlm plan`'s 8 steps. It takes about 10 conversational yes/answers, 3 trips to another terminal (login, the trial window, the final 300-character codex command) and about 16 permission prompts from the coding tool itself, one per command the agent runs. That matches the owner's complaint. The fix: make the CLI itself the product. Bare `cyrlm` runs detect, then one requirements form, then a ranked recipe table, then Enter to try (the coding tool opens in the same terminal, the way `ollama launch` does). After the trial a summary card and a rating key appear, then `s` to set up with ONE consolidated Y/n. cyrlm then runs the plan itself with cargo-style progress and a journal, so the setup can be resumed or undone, checks the result automatically, and Enter launches the tool on the real local model. That path is about 6 keystrokes plus one browser click and no copy-paste. The visible surface drops to 7 verbs: (none), find, try, setup, launch, status, key. The old commands become flags or hidden advanced commands. Login drops copy-paste: OpenRouter's documented OAuth PKCE flow accepts a localhost callback on any port and has a headless copy-a-code mode for SSH, so `cyrlm key` becomes a browser click and the key never passes through a chat or a terminal paste. Coding agents keep working through the same CLI run without prompts: `find --json`, then `try <id> --window`, then `setup <id> --yes --json`, which streams NDJSON events. That is about 3 tool approvals instead of about 16. For terminal input I recommend option (a), stdlib raw mode. I built and tested a prototype: 290 lines including the picker, color and fallback. It cross-compiles to all 6 release targets plus freebsd, and passed a Linux pseudo-terminal test (arrows, digits, Ctrl-C restore, NO_COLOR, piped input, CYRLM_NO_INPUT). Option (b), x/term, has the opposite problems: the latest version needs Go 1.26 and it adds x/sys, which breaks the project's stdlib-only rule. Option (c), bubbletea v2 or huh v2, needs Go 1.25.8 to 1.26 and 17 to 25 extra modules, too much for about 6 inline widgets. Running the binary also turned up concrete bloat and bugs: the speed shown changes between screens (224 vs 165 tok/s, 49 vs 40 tok/s), the same notes print twice, `doShare` prints the same message in both branches, `try` requires --harness, and spawning `claude` passes CLAUDECODE through, though Claude Code reportedly refuses to start nested while it is set. The biggest r/LocalLLaMA trick is also missing: cyrlm does not model MoE expert offload (--n-cpu-moe). It returns no recipe for Qwen3.6-35B-A3B on an 8 GB RTX 3070 Ti, while one blog post (Medium, unconfirmed) reports 19–43.8 tok/s with -ncmoe. Recipes should become a first-class type (model, file, runtime and 'tricks' such as MoE offload, q8 KV cache, MTP or other speculative decoding, YaRN, each with a 'needed here?' verdict) with a parser for pasted llama-server command lines and a 'claim vs predicted' check. Example: one blog's 140 tok/s on an RTX 3090 vs cyrlm's 177 ±45%.

### Implications
- Make bare `cyrlm` the product: guided home (detect with spinner → one requirements form → recipe table → Enter=try, s=setup). install.sh should `exec "$installed" </dev/tty` when /dev/tty exists, instead of printing the agent prompt, with CYRLM_NO_START=1 to opt out. README leads with 'run this in your terminal'; the agent prompt comes second.
- Cut the visible surface to 7 verbs (cyrlm, find, try, setup, launch, status, key). Keep serve, bridge, inspect and _bg under `help advanced`. Add stable recipe slugs `<model>/<quant>@<runtime>[+tricks]` and #1–#9 short references stored in ~/.cyrlm/last.json.
- Build internal/ui on the standard library (option a), starting from the tested prototype in (session scratch, not committed) rawproto/ui. Widgets: Select, Form (←→ value rows), Confirm (single key), Secret (masked paste), Spinner, Progress (bytes/rate/ETA), width-aware Table. Budget about 600 lines, inline only (no alt screen), prompts only when stdin and stdout are TTYs. Optionally use `stty` on darwin if raw SVC ioctl is unwanted. - Add a playground option (~/.cyrlm/playground: a small repo plus a fixed task) so trials can run without sending real code to OpenRouter and are comparable across recipes. Add a client-side trial budget (default $2; the server returns a visible error at the cap) and show spend in magenta.
- Replace `cyrlm login` with `cyrlm key`: OpenRouter OAuth PKCE (S256) with a callback on a random localhost port (documented as supported on any port), headless copy-code mode over SSH, and `--paste` as a masked-input fallback. Show credit via GET /api/v1/key. The key never appears in chats or agent transcripts.

- Add `cyrlm launch [tool]`: start the configured runtime (cyrlm bg logic) and the bridge in-process, then exec the tool with its env and -c flags. This removes the copy-paste of the ~300-character codex command and the separate bridge process the user has to manage.
- Agent contract: --json gives NDJSON on stdout (plan/step/check/done events) and human text on stderr. Exit codes 0/1/2/3 (needs user: key, sudo)/4 (not ready)/130. `--yes` approves exactly what `--dry-run` printed. Shrink agent_prompt.md to about 6 lines (find → try --window → setup --dry-run → one yes → setup --yes --json → launch).
- Fix the inconsistencies now, before the refactor: one tok/s figure everywhere (the 'deep in session' number, labelled), deduplicate the CPU-only notes, delete the identical doShare branches and the share/account surface, remove endpoint lists from the banner (keep under --verbose), and make --harness optional using detection plus prefs.
- Make the harness registry data-driven (JSON beside profiles.json), so new tools such as the requested 'Avalon' and 'Strata', once identified, are one entry each: protocols, prompt-size scenario, binary, connect method, detection env var.

## research:codebase-map

cyrlm is about 20.3k lines of Go (stdlib only) plus about 8.1k lines of tests across 23 packages. `go vet ./...` is clean, `gofmt` is clean, and `go test ./...` and `go test -race ./...` pass in all 19 packages that have tests (race run took 19 s). Coverage is high in the protocol, GGUF, hardware and setup packages (80–92%). It is lower in sim (64%), server (68%), predict (71%) and catalog (44%), and it is zero in cmd/cyrlm, which holds 2,941 lines and a lot of business logic. These parts are sound and worth keeping with small changes: llm types, the api/* protocol frontends (4.2k lines, 80–86%), the GGUF reader (2.3k lines, 91%, reads over HTTP Range), the hw probes (2.6k lines, 92%), the sim device and pacer, the server and bridge, the upstream client, tok, verify, and the roofline formulas in predict. What blocks a requirement-driven product built on recipes is how the code is organised, not the algorithms. (1) Ranking, choice of runtime, choice of quant file, building a model from a GGUF header, picking a trial stand-in, the harness compatibility check and detaching servers all live in package main. (2) Things that should be data are written as Go code: 13 hand-entered models, about 120 GPU specs, fitted efficiency tables, accuracy bands, the harness connect templates, about 950 lines of per-runtime setup builders, and runtime identity spread over about 9 maps. (3) The predictor has no idea of techniques. Expert offload is labelled 'no claim' and filtered out of recommendations. MTP and speculative decoding, YaRN, multi-GPU and the macOS wired-limit what-if are missing. vLLM is detected only. catalog.Model throws away the GGUF fields these features need (ExpertBytes/NonExpertBytes, NextNPredictLayers, rope scaling). (4) The catalog has 24 models, but the Hugging Face API, which works from this sandbox, can map a base repo to GGUF quant repos with exact file sizes. Together with OpenRouter's model list (hugging_face_id per model, likely), that can grow the catalog to hundreds of models. I also found a few concrete bugs and a list of dead code. Strata is real: Niko1221/Strata, a C++ engine plus a Python server with OpenAI- and Anthropic-compatible APIs, and its own `strata launch --plan / --yes / --output json`. I could not identify 'Avalon'. Below I propose a target layout (catalog, hardware, engines, techniques, predict, recipes, sim, serve, harness, setup with executor, verify, ui, app) with Go interfaces, and a migration order with 10 phases that keeps the CLI working at every step. It starts with characterisation (golden-output) tests on the commands so that logic can move out of main safely.

### Implications
- Target layout (keep the module, stdlib only). cmd/cyrlm should become a thin main of about 50 lines calling app.Run(os.Args). Proposed packages, each with its main contract:
- internal/app: one verb table, shared flag parsing and the flows (wizard, try, setup, verify, claim).
- internal/ui: ANSI colour with NO_COLOR, TTY detection via os.Stdout.Stat()&ModeCharDevice, tables, spinner, numbered pickers, --json mode.
- internal/catalog: Model and Quant types, embedded snapshot, OpenRouter index, HF resolver, FromGGUF.
- internal/hardware: hw probes, specs from devices.json, Target and SyntheticSystem moved out of predict, multi-GPU, CPU+GPU pair with PCIe bandwidth.
- internal/engines: profiles.json v2 plus detection, install, launch and technique flag templates per engine and version, including forks.
- internal/techniques: kvquant, expertoffload, specdecode (draft, MTP, ngram, eagle3), yarn, wiredlimit, flashattn, tensorsplit.
- internal/predict: pure math (Memory, a Timing interface, Accuracy bands from data, Scenario).
- internal/recipes: Recipe, Requirements, enumerate, evaluate, rank, explain, and community claims.
- internal/sim, internal/serve (server plus bridge), internal/api/*, internal/llm, internal/tok and internal/upstream: kept as they are.
- internal/harness: harnesses.json with connect templates, Launch, and binary detection so the harness can be auto-detected.
- internal/setup: planner (recipe → Plan) plus executor (runs steps under a consent policy, backups, undo log) plus proc (detach and bg from bridge.go).
- internal/verify: speed plus the compat.go harness check plus calibration write-back.
- internal/account: keys and config only; hide sharing until a server exists.
- Interfaces to define first:
- predict: `type Timing interface{ DecodeSec(depth int) float64; PrefillSec(from, to int) float64; LoadSec(warm bool) float64 }`. sim.Config.Timing becomes this interface, and techniques act as decorators, e.g. specdecode.Wrap(base, alpha, k, draftCostRatio).
- catalog: `type Source interface{ List(ctx) ([]Model, error); Resolve(ctx, ref string) (Model, error) }` with three implementations: Embedded, OpenRouter (cached at ~/.cyrlm/cache/openrouter.json) and HF (base → GGUF repos via `filter=base_model:quantized:<repo>&filter=gguf`, sizes via `?blobs=true`, geometry via gguf.OpenURL, splits merged with gguf.MergeSplits).
- techniques: `type Technique interface{ ID() string; Check(m catalog.Model, e engines.Engine, t hardware.Target) (ok bool, why string); ApplyMemory(*predict.MemoryPlan); WrapTiming(predict.Timing) predict.Timing; MaxContext(native int) int; Args(e engines.Engine) []string; Caveats() []string; Confidence() string }`.
- engines: data struct {ID, Name, Parent (fork of), Version range, Formats, APIs, Port, Platforms→backends, Detect{binaries, versionCmd, versionRegex, healthURL}, Install[os], Launch{bin, baseArgs, flagTemplates per technique}, Supports[technique]{flags, minVersion, confidence}, Defaults, Tuned, Perf} plus `type Adapter interface{ Plan(r recipes.Recipe, t hardware.Target) (setup.Plan, error) }`. There are two kinds of adapter. Composed adapters (llama.cpp, ik_llama.cpp, mlx-lm) build every step themselves. Delegated adapters wrap the engine's own installer and launcher: Strata via `strata launch --plan --output json` and then `--yes --no-tui`, Ollama via `ollama pull`/Modelfile, LM Studio via `lms get/load`.
- setup: `type Executor interface{ Run(ctx, Step, Policy) (Outcome, error) }` with `Policy{Approve map[Kind]Decision /* auto|ask|never */; DryRun bool; Yes bool}`. The default policy auto-approves read-only steps and cyrlm-owned files and asks once for the download plus service bundle. It never approves sudo or driver steps.
- Recipe and requirements as data. A Recipe is {id, engine@version, model id, quant (with sidecars mmproj/mtp/eagle3), techniques: [{id, params}], settings (ctx, kv, slots), harness}. Requirements are {harness (auto-detected), min_context (from the harness scenario), max_first_reply, max_turn, min_decode_tps, quality floor (min bits ≥4, or allow 3-bit), max_download_gb, prefer_installed, allow_experimental, engines, techniques}. Ranking: enumerate engines × quants × applicable technique combinations, predict each, filter by requirements, take the Pareto front on (task time, quality proxy, download size), then explain the result. Store community claims in claims.json as {source_url, hardware, recipe, claimed decode/prefill tok/s, date}. `cyrlm claim <id>` then runs a what-if on the claimed hardware and shows claimed vs predicted. Seed it with Strata's README tables and with Reddit posts the user can collect (reddit.com is blocked here).
- Prediction math to add, each change behind a confidence flag.
- Expert offload: split weights into GPU-resident (non-expert plus the experts of the remaining layers) and CPU-resident (ExpertBytes × fraction of layers under --n-cpu-moe). Decode ≈ gpuReadBytes/(effGPU·BW_gpu) + cpuExpertReadBytes/(effCPU·BW_ram). Prefill must account for expert weights crossing PCIe once a micro-batch is large, so Target needs RAM bandwidth and PCIe bandwidth. This needs catalog.Model to carry ExpertBytes, NonExpertBytes and per-layer expert bytes from gguf.Summary; regenerate models_gguf.json. It replaces the FitOffload no-claim hack so MoE-on-12 GB recipes become recommendable.
- Speculative decoding and MTP: speedup ≈ E/(1 + k·c) with E = (1−α^(k+1))/(1−α) (Leviathan et al. 2023, arXiv:2211.17192). Here k is the draft length (`--spec-draft-n-max`), c the draft-to-target cost ratio, and α the acceptance rate (low-confidence prior per model family and task). MTP is available when NextNPredictLayers > 0 or an mtp sidecar exists. The pacer should release tokens in accepted bursts.
- YaRN: max context becomes native × factor, with a caveat that it can hurt short-context quality.
- Wired limit: a Target transform that raises GPUMemBytes (what-if, needs sudo).
- Multi-GPU: sum VRAM, account for split overhead, use the minimum bandwidth across cards.

- sim.hasRollbackLimits should be `SWALayers > 0 || RecurrentLayers > 0`.
- runtime.Resolve fit_to_memory: when MaxFitCtx == 0, fall back to 4096 or flag 'does not fit' instead of using the native context.
- Remove the no-op --openrouter flag and merge --tuned/--defaults into one --defaults.

- Dedupe utf8.go, the shell quoting, the GGUF→Model mapping (one catalog.FromGGUF) and the formatting helpers.
- Replace the pinned install branch `ccr-db94bc6e-e47992` with releases/latest.
- Migration order, each phase shipping a working CLI.

### Open questions
- What is 'Avalon'? No local LLM engine or llama.cpp fork by that name turned up in searches; the user needs to give the repo URL.
- Is golang.org/x/term acceptable, given the stdlib-only rule? It gives masked key input and arrow-key pickers. Without it, pickers are numbered-line prompts and masking needs per-OS syscall code.
- What should the default consent policy be for low-friction setup? For example: auto-run downloads under N GB and cyrlm-owned files, ask once for service changes, never run sudo or driver steps. Should `--yes` cover everything except sudo?
- Where do acceptance-rate priors for speculative decoding and MTP come from (per model family, coding vs chat)? Is there public data, or must verify measure them and feed them back?
- How should expert offload be calibrated? The research dataset (565 rows) has no partial-offload runs (RESEARCH.md says 2–7× errors). We need a measurement plan or crowd data before making claims.
- vLLM support needs non-GGUF formats (AWQ/GPTQ/FP8/NVFP4 safetensors), an HF config.json geometry reader and its own efficiency fits. Is vLLM worth that scope now, or should it be detect-only plus a delegated setup?
- Can the OpenRouter /api/v1/models schema (hugging_face_id, context_length, endpoints with quantization) be confirmed from a network that can reach openrouter.ai? It is blocked here, so only third-party mirrors were checked.
- Should the trial still serve every protocol on port 11434 and impersonate Ollama by default? That can collide with a real Ollama, and `try` already falls back to 11435+.
- Should account sharing, the cyrlm upstream and login --account be removed or hidden until a server exists?


## research:niche-engines

I researched about 30 local inference engines (Nov 2026) and read 35+ READMEs and docs directly on raw.githubusercontent.com. Raw notes and the downloaded docs are in (session scratch, not committed) research/niche-engines.md (the docs themselves in research/dl/). The biggest speedups over stock llama.cpp and Ollama come from a new class of engines, each tuned for one model family, that run huge MoE models on a consumer GPU while the experts sit in system RAM. Strata, Avalon, Lamina, buun-llama-cpp, hipfire, Lucebox and DwarfStar/ds4 all do this for Qwen3.8-Flash-Next (125B, 512 experts, 10 active) and DeepSeek V4/V4.1 Flash. They combine a GPU cache of the hottest experts, the CPU computing the experts the cache misses at the same time, prompt processing (prefill) that streams experts over PCIe, a speculative drafter (MTP / DFlash2 / DSpark / prompt lookup), and quantized KV. Verified numbers from their own docs: Strata 87-93 t/s output on an RTX 5070 12 GB with 64 GB RAM (Q2_0), and Avalon 98 t/s on an RX 7900 XT with DDR4 and PCIe 3.0. Both are 2-10x stock llama.cpp on the same box (Lamina: 5.5-10.2x). For mid-size models, speculative-decoding engines claim 2.5-5x over llama.cpp: Splash on Mac (Qwen3.6-35B-A3B 175 vs 69 t/s), Lucebox and hipfire on AMD (Qwen3.8-27B 136-208 t/s), NInfer on RTX 5090, HyperQwen on a 3090. Almost all niche engines now serve OpenAI Chat, OpenAI Responses and Anthropic /v1/messages natively. So do mainline llama.cpp, SGLang, vLLM, mistral.rs, exo and Lemonade. The exceptions that still need triaLM's bridge are TabbyAPI, ik_llama.cpp (no /v1/messages), hipfire, mlx-lm, FastFlowLM and HyperQwen. Mainline llama.cpp has caught up on features (--moe-cache-mib, MTP / DFlash / DSpark / EAGLE3, Anthropic and Responses endpoints), so its forks are mostly drop-in llama-server binaries with better kernels, and a recipe can model them as an engine variant. Caveats: most niche engines are weeks old, have one maintainer and kernels written with AI help, ship model files in their own formats, and almost every speed number is self-reported. I mark each claim as [V] (read in the project's own docs) or [S] (third-party or search summary).

### Implications
- The roofline needs a three-tier MoE model or it will be far off for the fastest engines. Today decode is bytes/token divided by one bandwidth. Strata, Avalon, Lamina, buun, hipfire, Lucebox, ds4, KTransformers and mainline llama.cpp --moe-cache-mib all split per-token routed-expert bytes into three parts: (a) VRAM cache hits at GPU bandwidth; (b) misses computed by the CPU at RAM bandwidth, overlapped with the GPU (t = max(t_gpu, t_cpu) + sync); (c) when RAM is short, misses read from SSD (Avalon NVMe ~3.7 GB/s; Apple cannot overlap them, per flash-moe). New inputs needed: total and active expert bytes for the chosen quant, cache slots = (VRAM - dense - KV - reserve) / expert size, a hit-rate curve (skew, warm vs cold), measured RAM bandwidth, PCIe generation and width (prefill expert streaming and cache fills), and SSD read speed. Calibration anchors: the Strata DETAILS table (RTX 5070 12 GB / 64 GB DDR5, Q2_0 through IQ3_S), Avalon's tables by RAM size and context fill (RX 7900 XT, DDR4, PCIe 3.0), and buun's DeepSeek-V4 dual-3090 numbers.
- Speculative decoding is the main multiplier in nearly every fast engine (MTP, DFlash2, DSpark, EAGLE3, prompt lookup). It needs to be a recipe technique with a multiplier that depends on the workload: Avalon's MTP acceptance is 0.55-0.65 on prose and up to 0.95 on code or copied text; Strata gets 2.4-3.2 tokens per pass; HyperQwen 127 t/s normally vs 381 t/s when the answer quotes its prompt; Lucebox's HumanEval mean is far below its peak. triaLM's pacing in try mode should vary by content: edit and diff turns faster, reasoning prose slower. Verify should record accepted tokens per pass separately from raw t/s. Use averages, never peak numbers.
- API wiring: most niche engines natively serve OpenAI Chat, Responses and Anthropic /v1/messages, so they need no bridge. That covers Strata :8080, Lamina :8081, Splash :8000, ds4-server :8000, luce_server (--port), ninfer-serve :8080, mistral.rs :1234, exo :52415, Lemonade :13305, SGLang :30000, vLLM :8000, Sonar :2242, and mainline llama-server (Avalon/buun/Bee/strix-llama) :8080. Engines that still need triaLM's bridge for Claude Code: TabbyAPI :5000 (OpenAI only), ik_llama.cpp :8080 (chat + responses, no /v1/messages), hipfire :11435, mlx-lm :8080, FastFlowLM :52625, HyperQwen :18020, OVMS (/v3 prefix). Port collisions are common (8080 and 8000 are each used by several engines). Detection should probe /v1/models plus a HEAD on /v1/messages and /v1/responses rather than trusting default ports.
- A recipe must pin the engine and the exact model files together. Avalon needs its own IQ3_KS GGUF plus MTP head plus moe-cache-ranking.bin. ds4 accepts only its own GGUFs (qwen38-q2 is one 137 GiB file, 95 GiB of it n-grams left on disk). NInfer uses .ninfer artifacts, hipfire its MQ formats, ROCmFPX its own types. Strata recommends the ISTA GSQ-RCO packs plus a 28.8 GB n-gram table read from SSD each token, plus a 6 GB MTP layer. The fit check needs disk space and SSD speed as first-class requirements, not only VRAM/RAM.
- Use the engines' own machine-readable hooks for setup and verify instead of reimplementing them: `strata launch --plan --output json`, `strata launch --status`, `strata connect <claude-code|codex|opencode> --check --output json` (it already sends a prompt plus a tool call), `kt doctor`, `hipfire bench`, `ds4-eval`, Lemonade `/v1/system-info` and `/v1/pull`, buun/Avalon `-lv 4` logs (cache hits, fill failures). Lemonade can run any llama-server fork as its backend (LEMONADE_LLAMACPP_ROCM_BIN), so a fork can be a Lemonade recipe on AMD.
- Hardware routing (what a recipe ranker should suggest first). AMD RDNA3/RDNA4 dGPU with big RAM: Avalon (Flash-Next), hipfire, Lucebox, Strata HIP. Strix Halo: Lemonade (guest backends), strix-llama.cpp (Vulkan for decode), ds4/ds4fa (DeepSeek V4 ~32 t/s), Lucebox, hipfire (NPU prefill). NVIDIA 12-24 GB with 48-160 GB RAM: Strata, buun, ik_llama.cpp, Lamina (several GPUs), ExLlamaV3 (several GPUs). RTX 5090 or DGX Spark: NInfer, ds4, Lucebox. One 24 GB card with a dense 27B: HyperQwen (3090), hipfire/Lucebox (AMD), Splash (Mac). Mac: Splash (2.5-5x llama.cpp on supported models), ds4 (DeepSeek/GLM), strata-mlx, exo for clusters. Server CPU with AMX/AVX-512 and 256 GB+: KTransformers. Intel Arc: Strata SYCL, OpenVINO (IPEX-LLM is archived). Ryzen AI NPU: FastFlowLM, small models only.
- Mainline llama.cpp now has --moe-cache-mib, MTP/DFlash/DSpark/EAGLE3 spec types, Anthropic and Responses endpoints, and --fit by default. So triaLM should model most forks as 'llamacpp-compatible binary plus perf deltas': same CLI, same API, different efficiency constants and extra quant types. Keep separate engine models only for the non-llama.cpp engines (Strata, Splash, ds4, NInfer, hipfire, Lucebox, exllamav3, KTransformers).
- The try path through OpenRouter works for this model family: qwen/qwen3.8-flash maps to HF Qwen/Qwen3.8-Flash-Next, and deepseek/deepseek-v4.1-flash-1017, qwen/qwen3.8-27b and qwen/qwen3.6-35b-a3b also exist. - The fit model must keep a VRAM reserve and respect driver limits. Strata measured decode falling from 102 to 13.7 t/s at 0 MiB free. Strix Halo needs GTT/UMA settings. On Windows WDDM, pinning can fail.
- Verify should measure warm-state behaviour, not one cold request. Expert caches warm up over use (Avalon ~20 s after a cold start; Strata and buun learn heatmaps). Prompt-cache TTFT on follow-up turns differs a lot (Lamina 0.11-0.16 s vs llama.cpp 0.61-0.72 s; Splash cached 32K replay in 123-282 ms). Agent workloads are dominated by follow-up turns, so the simulator needs a cached-prefix TTFT term per engine.
- Risk and maturity: Avalon, Lamina, NInfer, strata-mlx, strix-llama.cpp and ds4 are days to weeks old, have one maintainer, and say openly that their kernels were AI-written. Several install with curl | bash. triaLM should pin versions or commits and SHA-check them, keep recipes in a remote data catalog so they can be updated without a binary release, and show 'self-reported' vs 'community-verified' badges on speed claims. Deprioritise (no): TensorRT-LLM, LMDeploy, MLC-LLM, PowerInfer, llamafile, IPEX-LLM (archived, security issues), ANE private-API engines, flash-moe (keep it only as an SSD-tier calibration point). Treat diffusion LLMs (DiffusionGemma 26B on vLLM, llama.cpp PR pending) as a model capability to watch, not an engine.

## research:charm-toad-ui

Recommendation: build triaLM's CLI on Charm's v2 stack. Use bubbletea v2.1.1, lipgloss v2.0.6, bubbles v2.2.1 and huh v2.0.3, all now under the charm.land vanity paths. Drive it from one root model and three output modes chosen at startup: TUI, plain, or JSON. Leave out glamour and wish.

The demo at (session scratch, not committed) research/charm-demo/main.go (339 lines, with go.mod and go.sum) is verified. It is a huh requirements form, then a lipgloss recipe table, then a huh confirm, then an inline bubbletea setup screen with a spinner and progress bar. It passes go mod tidy, go vet and go build, and cross-compiles for windows/amd64, darwin/arm64 and linux/arm64. In a pseudo-terminal it runs end to end without the alt screen, and finished steps stay in scrollback. Piped output has 0 escape bytes and --json gives clean JSON.

Binary size (linux/amd64, Go 1.26.0):
- Hello world: 2.41 MB (1.60 MB stripped).
- The demo: 7.31 MB (5.17 MB), so +4.90 MB (+3.57 MB stripped) over hello world.
- Linked into a copy of cyrlm: 12.34 MB becomes 15.37 MB (+3.03 MB, +25%); stripped 8.73 MB becomes 10.98 MB (+2.25 MB).
- glamour alone adds about +12.3 MB.

Two blockers for the repo:
- **Go version:** bubbletea v2.0.10 and later require go 1.26.0, but the repo is on 1.24.7. The default GOTOOLCHAIN=auto fetched Go 1.26.0 without trouble.
- **Dependencies:** cyrlm currently has no third-party modules; this brings in 38.

Three pitfalls were reproduced:
- colorprofile v0.4.3 ignores NO_COLOR=yes or NO_COLOR=anything on a TTY. The demo works around it.
- lipgloss.HasDarkBackground used on its own reads stdin for up to 2s. On a terminal that never answers DA1 (a standard terminal query), keys typed in that window are lost.
- Sequential huh forms each start their own tea.Program.

Toad is Python plus Textual 8.2.7, not Charm. Its feel comes from:
- flicker-free updates to only the parts of the screen that changed;
- streaming markdown that re-renders only the last block;
- a footer that always shows the keys relevant to the current context.

The equivalent Go tools are bubbletea v2's new renderer (which uses synchronized output, mode 2026) and an inline layout.

### Implications
- Moving the repo to Charm v2 means bumping go.mod from 1.24.7 to 1.26 for bubbletea v2.0.10 and later (current is v2.1.1). The alternative is pinning bubbletea ≤ v2.0.8 to stay on Go 1.25. Either way it adds about 37 third-party modules to what is currently a dependency-free repo.
- Expect the release binary to grow by about +2.25 MB stripped (+26%) for the huh+bubbletea+bubbles+lipgloss stack. Adding glamour would add roughly another 9.7 MB, so leave it out.
- Toad itself is Python plus Textual and cannot be reused. Its qualities can be reproduced in Go: inline output that keeps scrollback, small partial redraws (bubbletea v2's new renderer with mode 2026), a context-sensitive key footer, and minimal chrome.
- Split rendering from the core logic (data structs plus event channel), with three renderers: JSON, plain, and TUI. This lets coding agents drive every command with --json/--yes and no TTY, while humans get the TUI from the same code paths.
- Use one long-lived root bubbletea model for the whole flow rather than a chain of separate huh/tea programs. That avoids repeated raw-mode switching and terminal queries, and the keystroke loss seen when a terminal is slow to answer the background query.
- triaLM must implement NO_COLOR itself, because colorprofile v0.4.3 ignores values like NO_COLOR=yes. It must also keep the pacing server's logs and installer child-process output away from the terminal while the TUI runs (log to a file plus an in-app viewport, as crush does with its stderr detach).

### Open questions
- Should the repo move to Go 1.26 (latest bubbletea v2.1.x), or stay on Go 1.25 with bubbletea ≤ v2.0.8? CI and install scripts need the same bump either way.
- Keep stdlib flag, or adopt fang/cobra for styled help, errors and manpages? Standalone it costs +2.7 MB stripped; the size inside cyrlm was not measured.
- Should the live trial dashboard use the alt screen (full-screen, like crush) or stay inline (scrollback, like gum)? The recommendation is alt screen only for the dashboard, but the owner may want inline everywhere for a crisper feel.
- Nothing was run on a real Windows console or Windows Terminal; only cross-compiled. crush claims PowerShell support, but huh, the progress bar and the glyphs (›, ✓, the spinner) should be checked on Windows before release.
- Several hosts were blocked from this sandbox: willmcgugan.github.io, charm.land/blog, simonwillison.net, textual.textualize.io and infoq.com (DNS failure), plus github.com and api.github.com (403). So Toad's design rationale and Charm's v2 blog are cited only via search summaries. The user said they will approve a network change request; the orchestrator could raise one adding willmcgugan.github.io, charm.land and simonwillison.net to read the primary sources.


## research:openrouter-live

I ran a live coverage analysis of OpenRouter's 458-model snapshot (2026-11-06) against Hugging Face. The work used three cached python3 -I scripts with standard-library urllib, about 3 requests per second, and roughly 1,580 requests (1,688 cache entries, 84 MB). The scripts are in (session scratch, not committed) research/scripts/: or_hf_map.py, or_hf_lineage.py, or_hf_stats.py and or_coding_endpoints.py.

Scope: 172 OpenRouter rows have a hugging_face_id. They collapse to 155 unique HF repos and 151 base OpenRouter models (plus 10 `:free` and 11 `:batch` variants).

Headline numbers (unique HF repos):
- **Reachable on HF:** 151/155. 4 return 401 (not public).
- **GGUF repo found by exact-name match:** 147/155. 130 of those are from core quantizers: unsloth 105, bartowski 22, ggml-org 3.
- **MLX:** 120/155 have an mlx-community repo (114 by name search, 104 by lineage tag, union 120). 140 have MLX from any author.
- **Size:** 69 are 40B total parameters or smaller.
- **Tools:** 122 support tools on OpenRouter.
- **Intersections:** 44 are 40B or smaller with tools and GGUF (38 also have MLX). 59 are 130B or smaller with tools and GGUF. 95 are MoE.
- **GGUF headers:** read by HTTP Range for 145 of 147 repos. 156 reads needed only 256 KiB; 2 needed 4 MiB.
- **config.json vs GGUF disagreements:**
  - 17 layer-count mismatches, every one explained by multi-token-prediction (MTP) layers being appended to block_count.
  - 30 KV-head mismatches, from MLA models (GGUF stores 1) and per-layer arrays.
  - 27 head_dim mismatches, from MLA latent sizes (576/512).
  - 23 models whose GGUF stores per-layer head_count_kv arrays.
  - 11 context-length mismatches.
- **Provider endpoints:** 851 across the 151 base models. Quantization: fp8 331, unknown 241, fp4 143, bf16 70, mxfp4 24, int4 18, nvfp4 15, fp16 8, fp32 1. latency_last_30m and throughput_last_30m are null on every endpoint.
- **Naive GGUF search is unreliable:** taking the top result by downloads picks a wrong repo (finetunes, uncensored variants) for 45/150 models.
- **Current catalog is stale:** 8 of the 24 OpenRouter IDs in the current cyrlm catalog do not exist on OpenRouter.

The full mapping is in (session scratch, not committed) research/openrouter-hf-gguf-map.json. It has 172 records with all requested fields, plus provider details, GGUF geometry, sidecar files, lineage results and ctx from 4 sources. Aggregates are in (session scratch, not committed) research/openrouter-hf-gguf-stats.json and openrouter-hf-lineage-stats.json in the same folder.

The proposed catalog build is: build-time generated JSON, embedded with go:embed, from OpenRouter, then HF lineage plus name matching, then config.json, then GGUF header range reads. A runtime refresh fetches OpenRouter once a day and fetches HF only for the selected model, keyed by repo sha. A small set of architectures (DeepSeek-V4, MiMo-V2, Kimi-K3, GLM-5.3-Flash, Ling-3.0, Gemma-4, Llama-4) need layout plugins keyed by architecture name, because neither config.json nor a generic GGUF reader gives their per-layer KV layout.

### Implications
- Generate the catalog from OpenRouter rather than hand lists. 8 of the 24 current OpenRouter IDs are dead, so add a CI gate that fails when an id is not in /api/v1/models.
- The 'try' feature should pin providers with provider.order/only (endpoint tag), quantizations[] and require_parameters:true. Choose the provider whose ctx is at least the planned local ctx and whose precision is closest to the native or local weights. 64 models have providers with different context lengths, and 241 of 851 endpoints report quantization 'unknown'.
- For :free and :batch variants, always fetch /api/v1/models/<variant-id>/endpoints. links.details silently returns the paid or base providers, or none.
- Do not use OpenRouter latency or throughput fields for pacing. They were null on all 851 endpoints in this run, so pacing must come from triaLM's own roofline model.
- GGUF discovery needs lineage plus exact-name matching plus an author allowlist plus direct probes. Lineage alone admits finetunes (743 tagged), and top-by-downloads is wrong 30% of the time.
- Sidecars (MTP, DFlash, DSpark, EAGLE3 drafts, mmproj, vision encoders) are now common inside GGUF repos and as separate -MTP-GGUF repos. Classify them by header arch and expose them as speculative-decoding recipe assets.
- GGUF block_count includes MTP layers (17 models). Exclude nextn layers from per-token bytes when MTP is off, and include them when the recipe enables MTP.
- A local recipe can only match an OpenRouter-served context through YaRN for 15 rows where providers exceed config max_position_embeddings. The catalog must store ctx per source (OpenRouter per provider, config, GGUF) and recipes should state which one they use.
- Arch-specific layout plugins are required for about 23 hybrid or sliding-window architectures and 29 MLA architectures. Anything else should be flagged geometry_unverified and calibrated by the verify step.
- Local-relevant scope today is 44 tool-capable models of 40B or smaller with GGUF (38 with MLX), plus 13 MoE models of 40-130B for expert offload.

### Open questions
- Does OpenRouter return latency_last_30m and throughput_last_30m with an API key, or from another endpoint? They were null here unauthenticated.
- Exact active parameters and expert/non-expert bytes per quant need full tensor-table reads (several MB per file). I read only the KV sections (256 KiB), so params_active is partly name-derived (30) and partly a config estimate (59) that overestimates hybrids.
- Which of the new GGUF arch strings (deepseek4, deepseek41, kimi-k3, kimi-k31, glm5-next, glm-dsa, mimo2, bailingmoe3, step5, inkling, muse-spark, dflash, dspark) are supported by upstream llama.cpp versus forks (e.g. antirez's DeepSeek-V4.1 GGUF, whose header has no <arch>.block_count within 4 MiB)? This should be checked against llama.cpp source on raw.githubusercontent.com.
- How should DeepSeek-V4's compressed or hashed attention (attention.compress_ratios, hash_layer_count) translate into KV bytes per token? That needs llama.cpp implementation details.
- Four OpenRouter hugging_face_ids return 401 (Hy4, Nemotron-3.5-Super-VL, two schematron-v2 models). Should triaLM list them as cloud-only until weights are public?
- How should triaLM resolve the 5 or more open-weight OpenRouter models that lack hugging_face_id (minimax-m1, Cohere command-r family, ling-3.1-flash)? A curated override table or a name search?
- Range reads to the legacy cdn-lfs-us-1.hf.co host were blocked by this sandbox proxy (Xet-backed files worked). This needs checking from a normal network so triaLM handles both HF storage backends.
- All numbers come from a single snapshot (2026-11-06) and will drift. Decide the refresh cadence and whether the embedded catalog should carry a generated_at date plus a staleness warning.
